# Fixture Policy

All test fixtures in this repository must be **fictional and synthetic**.

## Rules

1. **No real machine data.** Never copy real `.desktop` files, `.lnk` files, SSH configuration, hostnames, usernames, IP addresses, tokens, password files, or private paths from any developer machine into the repository.
2. **Fictional domains only.** Use `example.com`, `example.org`, `example.net` (RFC 2606) for hostnames and email domains (e.g., `alice@example.com`, `build-server.example.com`).
3. **Documentation IP ranges only.** Use RFC 5737 IPv4 (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`) and RFC 3849 IPv6 (`2001:db8::/32`) for any addresses appearing in fixtures or docs.
4. **Fictional principals.** Usernames, hosts, and display names must be obviously fictional (e.g., `alice`, `Org.Example.Tool`).
5. **Generated Windows fixtures preferred.** Synthetic `.lnk` files should be generated by a committed generator script at test time rather than committing opaque binaries where feasible. If a binary fixture is unavoidable, document its provenance and generation command.
6. **No credentials.** Fixtures must never contain secrets, private keys, tokens, or password material. Secret-shaped strings in export/import tests must be drawn from a fixture corpus of dummy values and caught by the export linter.
7. **No real `.desktop`/`user-dirs.dirs` content.** Linux fixtures must be hand-crafted fictional entries; never snapshot a developer's `~/.local/share/applications` or `user-dirs.dirs`.
8. **No screenshots/videos from a real environment.** Manual-system evidence (counts, dry-run notes) must stay outside Git unless fully sanitized to fictional data.
9. **Provenance documented.** Each fixture directory must have a manifest describing expected classifications and the fictional data contract it exercises.
10. **Public-safety review.** New fixtures are reviewed against `docs/security/PUBLIC_REPOSITORY_SAFETY.md` and `tools/check-public-safety.sh` before merge.
